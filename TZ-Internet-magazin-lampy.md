# Техническое задание  
## Интернет-магазин продукции завода лампочек (микросервисная архитектура)

**Версия:** 1.0  
**Дата:** 10.04.2026  
**Объём каталога:** 20 наименований (типовых позиций номенклатуры завода)

---

## 1. Цели и границы проекта

### 1.1. Цель
Разработать веб-приложение интернет-магазина с каталогом, корзиной, оформлением заказа и административной панелью для управления товарами и заказами. Система строится как набор микросервисов с отдельными базами данных и REST API.

### 1.2. Входит в объём
- Витрина: каталог, карточка товара, корзина, оформление заказа, страница подтверждения заказа.
- Управление: CRUD товаров, просмотр и смена статусов заказов, базовая модерация видимости товаров.
- Документация по каждому микросервису: структура БД + коллекция Postman (эквивалент: описание запросов в таблицах ниже с переносом в Postman вручную или импорт из OpenAPI, если команда генерирует его из кода).

### 1.3. Не входит (можно расширить в следующих итерациях)
- Реальная оплата (интеграция с эквайрингом) — на этапе ТЗ достаточно статуса «ожидает оплаты» / «оплачен» как бизнес-статуса без платёжного шлюза.
- Доставка с расчётом тарифов транспортных компаний — фиксированные поля адреса и комментария к доставке.
- Многоязычность, личный кабинет покупателя с историей заказов (по желанию команды; для выполнения ДЗ 1 достаточно подтверждения по номеру заказа на экране).

## 2. Роли и сценарии

| Роль | Описание |
|------|----------|
| **Гость** | Просмотр каталога и карточек товаров. |
| **Покупатель** | Добавление в корзину, оформление заказа, просмотр подтверждения с номером заказа. |
| **Администратор** | Вход в админку, CRUD товаров, просмотр списка заказов, смена статуса заказа. |

Идентификация покупателя на этапе ТЗ: **анонимная корзина**, привязанная к `cart_id` (UUID в cookie или localStorage на клиенте), передаваемому в API.

## 4. Архитектура микросервисов

| Сервис | Назначение | Собственная БД |
|--------|------------|----------------|
| **catalog-service** | Каталог товаров, категории, цены, остатки, публикация на витрине | `catalog_db` |
| **order-service** | Корзина, заказы, позиции заказа, статусы | `order_db` |
| **admin-service** | Аутентификация администратора, прокси/агрегация вызовов к catalog и order для админ-UI (или тонкий BFF) | `admin_db` |

**Взаимодействие:** витрина обращается к **catalog-service** и **order-service** по публичным API. Клиент админки обращается к **admin-service**, который с внутренним или сервисным токеном вызывает **catalog-service** и **order-service**. Альтернатива (допустима в реализации ДЗ 2–4): админ-фронтенд вызывает catalog и order напрямую при единой SSO-схеме — в ТЗ зафиксирован вариант с **admin-service** как единой точкой для админских операций.

**Согласованность:** при создании заказа **order-service** запрашивает у **catalog-service** актуальные цены и наличие по `product_id` (или принимает снимок цен с клиента с серверной валидацией — в ТЗ выбран вариант **серверной проверки по каталогу**).

## 5. Микросервис: catalog-service

### 5.1. Назначение
Хранение номенклатуры завода лампочек, категорий, цен, остатков и признака публикации на витрине.

### 5.2. Структура БД (`catalog_db`)

**Таблица `categories`**

| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID, PK | Идентификатор |
| name | VARCHAR(128) | Название (например: «Лампы накаливания», «Светодиодные») |
| slug | VARCHAR(128), UNIQUE | ЧПУ для URL |
| sort_order | INT | Порядок сортировки |

**Таблица `products`**

| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID, PK | Идентификатор товара |
| category_id | UUID, FK → categories.id | Категория |
| sku | VARCHAR(64), UNIQUE | Артикул завода |
| name | VARCHAR(255) | Наименование |
| description | TEXT | Описание |
| price | DECIMAL(12,2) | Цена в рублях |
| stock_qty | INT | Остаток на складе |
| image_url | VARCHAR(512) | URL основного изображения |
| is_published | BOOLEAN | Видимость на витрине |
| created_at | TIMESTAMPTZ | Создание |
| updated_at | TIMESTAMPTZ | Обновление |

**Индексы:** `products(category_id)`, `products(is_published)`, полнотекстовый поиск по `name` — по решению команды (например, GIN/tsvector в PostgreSQL или `ILIKE` на MVP).

**Связь с прототипами:** поля P1–P3 и A3 покрываются таблицей `products` и `categories`.

### 5.3. API catalog-service (REST, JSON)

Базовый URL (пример): `https://api.example.com/catalog`  
Заголовок: `Content-Type: application/json`

| Метод | Путь | Назначение |
|-------|------|------------|
| GET | `/api/v1/categories` | Список категорий |
| GET | `/api/v1/products` | Список товаров (`?category_id=`, `?search=`, `?published_only=true`) |
| GET | `/api/v1/products/{id}` | Карточка товара |
| POST | `/api/v1/products` | Создание товара (админ) |
| PUT | `/api/v1/products/{id}` | Обновление (админ) |
| PATCH | `/api/v1/products/{id}/publish` | Включить на витрине `{ "is_published": true }` |
| DELETE | `/api/v1/products/{id}` | Удаление (админ; допустимо мягкое: `is_published=false`) |

**Примеры тел запросов**

Создание/обновление товара (POST/PUT):

```json
{
  "category_id": "uuid",
  "sku": "LED-A60-10W-4000K",
  "name": "Светодиодная лампа A60 10Вт 4000K",
  "description": "…",
  "price": 189.00,
  "stock_qty": 120,
  "image_url": "https://cdn.example.com/lamps/a60-10w.jpg",
  "is_published": true
}
```

Ответ списка (фрагмент):

```json
{
  "items": [
    {
      "id": "uuid",
      "name": "…",
      "price": 189.00,
      "image_url": "…",
      "category_id": "uuid"
    }
  ],
  "total": 20
}
```

## 6. Микросервис: order-service

### 6.1. Назначение
Корзина (до оформления), заказы, позиции заказа, жизненный цикл статусов.

### 6.2. Структура БД (`order_db`)

**Таблица `carts`**

| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID, PK | Идентификатор корзины |
| client_cart_key | VARCHAR(64), UNIQUE | Ключ из cookie/клиента |
| created_at | TIMESTAMPTZ | Создание |
| updated_at | TIMESTAMPTZ | Обновление |

**Таблица `cart_items`**

| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID, PK | |
| cart_id | UUID, FK → carts.id | |
| product_id | UUID | Ссылка на товар в catalog (без FK между БД — контроль на уровне приложения) |
| quantity | INT | Количество |
| unit_price_snapshot | DECIMAL(12,2) | Цена на момент добавления (опционально; иначе пересчёт при чекауте) |

**Таблица `orders`**

| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID, PK | |
| order_number | VARCHAR(32), UNIQUE | Человекочитаемый номер (например, ORD-2026-00001) |
| status | VARCHAR(32) | См. машину состояний |
| customer_name | VARCHAR(255) | ФИО |
| customer_phone | VARCHAR(32) | Телефон |
| customer_email | VARCHAR(255) | Email |
| delivery_address | TEXT | Адрес |
| delivery_comment | TEXT | Комментарий |
| total_amount | DECIMAL(12,2) | Итоговая сумма |
| cart_id | UUID, nullable | Связь с исходной корзиной |
| created_at | TIMESTAMPTZ | |
| updated_at | TIMESTAMPTZ | |

**Таблица `order_items`**

| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID, PK | |
| order_id | UUID, FK → orders.id | |
| product_id | UUID | |
| product_name_snapshot | VARCHAR(255) | Наименование на момент заказа |
| quantity | INT | |
| unit_price | DECIMAL(12,2) | Цена в заказе |
| line_total | DECIMAL(12,2) | Сумма строки |

**Статусы заказа (`orders.status`)**

| Статус | Описание |
|--------|----------|
| `draft` | Технический (не используется для оформленных; опционально) |
| `new` | Принят, ожидает обработки |
| `confirmed` | Подтверждён менеджером |
| `paid` | Оплачен (в т.ч. вручную отмеченный админом) |
| `shipped` | Отгружен |
| `completed` | Завершён |
| `cancelled` | Отменён |

**Допустимые переходы (для админки и API)**

- `new` → `confirmed`, `cancelled`
- `confirmed` → `paid`, `cancelled`
- `paid` → `shipped`, `cancelled`
- `shipped` → `completed`
- `completed`, `cancelled` — финальные (без переходов наружу)

### 6.3. API order-service (REST, JSON)

Базовый URL: `https://api.example.com/orders`

| Метод | Путь | Назначение |
|-------|------|------------|
| GET | `/api/v1/cart` | Корзина по `X-Cart-Key` или query `cart_key` |
| POST | `/api/v1/cart/items` | Добавить позицию `{ "product_id", "quantity" }` |
| PATCH | `/api/v1/cart/items/{item_id}` | Изменить количество |
| DELETE | `/api/v1/cart/items/{item_id}` | Удалить позицию |
| POST | `/api/v1/orders` | Оформить заказ из корзины: контакты + адрес; тело ниже |
| GET | `/api/v1/orders/{id}` | Заказ по UUID (для подтверждения на витрине) |
| GET | `/api/v1/orders/by-number/{order_number}` | Альтернатива поиска по номеру |
| GET | `/api/v1/admin/orders` | Список для админки (`?status=`, пагинация) |
| GET | `/api/v1/admin/orders/{id}` | Детали заказа |
| PATCH | `/api/v1/admin/orders/{id}/status` | Смена статуса `{ "status": "confirmed" }` |

**Оформление заказа (POST `/api/v1/orders`)**

```json
{
  "cart_key": "string-from-client",
  "customer_name": "Иванов Иван",
  "customer_phone": "+79001234567",
  "customer_email": "user@mail.ru",
  "delivery_address": "г. Москва, ул. …",
  "delivery_comment": "Домофон не работает"
}
```

Сервер: валидирует корзину, для каждой позиции запрашивает актуальные цену и остаток у catalog-service, считает `total_amount`, создаёт `order` + `order_items`, очищает корзину.

## 7. Микросервис: admin-service

### 7.1. Назначение
Единая точка входа для админ-панели: аутентификация администратора, проксирование к защищённым операциям catalog и order (создание/изменение товаров, список заказов, смена статуса).

### 7.2. Структура БД (`admin_db`)

**Таблица `admin_users`**

| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID, PK | |
| login | VARCHAR(64), UNIQUE | Логин |
| password_hash | VARCHAR(255) | Хэш пароля (например, bcrypt) |
| full_name | VARCHAR(255) | ФИО для отображения |
| is_active | BOOLEAN | |
| created_at | TIMESTAMPTZ | |

**Таблица `refresh_tokens` (опционально)**

| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID, PK | |
| admin_user_id | UUID, FK | |
| token_hash | VARCHAR(255) | |
| expires_at | TIMESTAMPTZ | |

### 7.3. API admin-service

Базовый URL: `https://api.example.com/admin`

| Метод | Путь | Назначение |
|-------|------|------------|
| POST | `/api/v1/auth/login` | `{ "login", "password" }` → JWT access (и refresh при необходимости) |
| POST | `/api/v1/auth/logout` | Инвалидация сессии/refresh |
| GET | `/api/v1/me` | Текущий пользователь по Bearer JWT |

Далее — обёртки с пробросом `Authorization: Bearer <token>` к внутренним вызовам:

| Метод | Путь | Проброс к |
|-------|------|-----------|
| * | `/api/v1/catalog/*` | catalog-service |
| * | `/api/v1/orders/*` | order-service (admin-эндпоинты) |

Либо явные агрегированные маршруты:

| POST | `/api/v1/products` | Создание товара (вызов catalog) |
| PUT | `/api/v1/products/{id}` | Обновление |
| GET | `/api/v1/orders` | Список заказов |
| PATCH | `/api/v1/orders/{id}/status` | Смена статуса |

## 8. Нефункциональные требования

- **Формат API:** JSON, UTF-8, коды HTTP по семантике REST.
- **Ошибки:** единый формат `{ "error": { "code": "string", "message": "string" } }`.
- **Безопасность:** HTTPS; пароли не хранить в открытом виде; ограничение частоты запросов на логин (по возможности).
- **Время:** серверное время UTC в БД, отображение на клиенте в локали пользователя.
